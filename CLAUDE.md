# ARI: code notes for Claude Code

An installable web app (PWA) for capturing material in the field and revisiting it later. Plain JavaScript + Vite, no framework. The project plan (concept, decisions, milestones) is kept outside this repository and is private; the owner will provide it when needed. This repository is **public**.

## How to work with the owner
- The owner is learning by building. Before each step, explain what you are about to do. Explain every file you create: what it is for and what would break without it.
- Take small steps; finish one slice end to end before starting the next. Do not build features from later milestones unless asked.
- Walk the owner through anything they must do themselves (signing in, approving downloads). Ask before downloading anything or publishing anything.
- Prefer simple, low-maintenance solutions. Automate chores; keep human steps few and light.

## Rules
- **Never put an AI API key, or any secret, in this repo or in the app code.** The repo is public and the app runs in the browser, so anything in the code is readable by anyone. When AI features arrive, calls need a small go-between server or a key each user enters themselves.
- Captured user data stays on the user's devices. Only code is public.
- `base` in `vite.config.js` must equal the GitHub repository name (`ari`).
- Git identity is set per repository (not globally): name "Nemo", GitHub noreply email. Do not use a real email.

## Commands
- `npm run dev`: local test server.
- `npm run build`: package into `dist/`.
- `npm run preview`: serve `dist/` locally; the address includes `/ari/`.
- Deploy: `git push` to `main`. GitHub Actions builds and publishes to Pages in about a minute.

### Capture fields (schemaVersion 2; fields approved 2026-10-11, changed 2026-10-12)
A capture is one photo, voice memo or text note as it arrived. It was called a "card" until 2026-10-12; the name "card" is kept free for a later milestone. Every capture has all these fields; "optional" means the value is `null` (or `''` for `text`) when unused.
- `id`: random unique ID made on the phone (`crypto.randomUUID()`), so imports never collide and importing twice skips duplicates.
- `schemaVersion`: `2`. So old captures can be migrated (new fields arrive through a new version). Version 1 had `gist` and `status` and no `deleted`; `upgradeCapture` in `src/captures.js` converts them (`gist` becomes `title`, `status` is dropped, `deleted` is `null`). The `updated` field is not typed by anyone: it is the time of the capture's newest change record. The capture record itself is the current state worked out from its change records (see "Change records").
- `kind`: `text`, `photo` or `audio`.
- `created`, `updated`: times as ISO 8601 UTC strings.
- `text`: the note's text. **Allowed on every kind** (a caption or dictated note on a photo or recording). `''` when none.
- `title`: optional one-line title in the owner's own words.
- `source`: optional free text.
- `place`: optional text the owner types (for example "Central Library, 2nd floor"). Separate from `location`.
- `location`: optional `{ lat, lon, accuracy, at }`: latitude, longitude, accuracy in meters, time measured (ISO string). `null` if denied or no signal. The capture is saved first and location attached when it arrives, so capture never waits for GPS.
- `media`: optional `{ mimeType, size }`. The blob itself is stored in a separate object store keyed by the capture `id`, so listing the inbox never loads photos or recordings. `mimeType` comes from the recorded data, never from `recorder.mimeType` (empty on iOS at start).
- `deleted`: `null`, or the time the capture was moved to the trash. Trashed captures are hidden from the inbox, listed under Trash, and can be restored; moving to or from the trash sets `updated`, so the next export carries it.
- Left out on purpose: tags (no tag upkeep; they matter once AI suggests them), change history, a reliability note (the owner writes it in `text` when it matters; add a field via `schemaVersion` if needed).
- Nothing is permanently deleted in the app yet (no "delete forever", so trashed photos still use space). The rule for emptying the trash is not decided.
- Audio cleanup rule: decide later.

### Change records and export files (format `ari-changes` version 1; the three earlier formats still import)
- **A change record** is one small JSON object: `{ id, at, device, by, target: { type: "capture", id }, op, fields }`. `id` is random (or `m-<capture id>-<updated>` for a record made from a capture that existed before records). `at` is the device clock as an ISO time, strictly increasing on one device. `device` is this device's random id. `by` is `nemo`, `migration` (`ai` and `trace` are reserved). `op` is `create` (all of `kind, created, text, title, source, place, location, media, deleted`) or `set` (only some of `text, title, source, place, location, deleted`; `kind`, `created` and `media` never change). Records are only ever added, never edited or removed.
- **Combining records** (`foldCapture` in `src/changes.js`): sort a capture's records by `at`, ties by `id`; for each field the newest value wins. The result does not depend on the order records arrived in. A record whose capture has not arrived yet waits in the history and takes effect when the capture's `create` record arrives. A record already in the history changes nothing, so importing twice is harmless.
- **What gets recorded:** saving a note, photo or recording (`create`); the Edit form (only the fields whose value really changed, so an untouched field is never re-stamped); a location arriving; Move to trash and Restore (`set deleted`). Saving an Edit form with no changes records nothing.
- **Clocks:** merging trusts each device's clock. A device with a wrong clock can make its edits win or lose wrongly. Accepted for now.
- **Export files:** one index file per batch, plus each photo or recording as a normal file next to it. Index name: `ari-changes-<device id, first 8 characters>-<export time, colons as dashes>-<n>of<N>.json`. Media name: `ari-<created, colons as dashes>-<first 8 characters of capture id>.<ext>` (extension from the mime type; `bin` if unknown). Nothing is ever overwritten: names carry the device and the time. The index holds `{ format: "ari-changes", formatVersion: 1, device, exportedAt, changes: [ { change: {...record...}, mediaFile: "<file name>" | null }, ... ] }`; `mediaFile` is only set on `create` records.
- **Snapshot file:** the first batch of every export also carries `ari-snapshot-<device>-<time>.json` (`format: "ari-snapshot"`): the current state of every capture, trashed ones included, pretty-printed, with the media file name of each. It is for reading by hand. Import recognises it and ignores it.
- **Which records:** "Export new changes" = records not in the `sent` store; "Export all" = every record. A record is marked sent only after its batch's share succeeded (`navigator.share` resolved); cancelled or failed shares mark nothing. Records that came in through an import are marked sent, so they are not sent back out. Caveat: "shared" means the share sheet reported success, not that a file is known to have arrived.
- **Batches:** a record and its media file stay in the same batch. Limit 25 MB per batch (`MAX_BATCH_BYTES` in `export.js`) and 100 files including the index (sanity limit). **The 25 MB figure is a guess: the largest file ever shared in a test was about 100 KB.** Photos are shrunk to about 0.5 MB. The first real export of several photos is the real test.
- **Import:** pick all the files at once, including ones imported before. Each item is checked on its own, so one bad item does not stop the others; everything valid is applied in one all-or-nothing step. Media is matched by the file name in the index and checked by size; a file for a capture that has none yet is stored even when the capture's record is already known (this restores a missing photo). Report: "N new change(s) applied, N already known", plus files stored, captures waiting for their `create` record, snapshots ignored, and problems. Files made by a newer app version are refused.
- **Earlier formats** (read, never written): `ari-captures` v1 (one index per batch, whole captures), `ari-cards` v2 (the same, from when captures were called cards) and `ari-card` v1 (one file per card). Each capture in them becomes one `create` record with `by: migration` and `at` = its `updated`, so the same old capture arriving twice is recognised and a newer version of it wins field by field.
- A database upgrade to version 4 gave every existing capture one such `create` record, and carried over which captures had been exported.
- Export/import stays as a permanent option and backup even after automatic sync exists.
- Considered and not built: one big database file overwritten on every export (the iOS share sheet cannot overwrite a file; it makes "name 2" copies) and photos packed inside a file (memory risk, and photos could no longer be opened directly in OneDrive). Ideas for later: a notes-only Markdown export for other tools.

### Sync (recorded 2026-10-11, NOT built; its own milestone after M1, before the board)
- Goal: the same cards on phone and laptop, tied to a login.
- Chosen direction: each user's own cloud. Log in with Microsoft and store cards and media in an app folder in the user's own OneDrive through Microsoft Graph. No server of the owner's, no storage costs, and the owner never holds anyone's data. Google Drive maybe later.
- Each device keeps its local copy (offline first); sync exchanges changes when online. `src/storage.js` is the one file the local database lives in.
- To work out when we get there: Microsoft app registration and the login flow in iPhone home-screen apps; how edits from two devices are merged (newer `updated` wins as a start); how deletions sync; what happens offline.
- Alternatives considered and set aside: a hosted backend (Supabase/Firebase: the owner would hold everyone's data and pay as users grow) and Dexie Cloud (least code, but paid beyond a free tier and tied to one company).
- Direction recorded 2026-10-12: edits are small change records (built, see "Change records"). Until automatic sync exists, devices exchange them by hand through export and import in one OneDrive folder. Automatic sync (this milestone) should carry the same records.
- Rule that still applies: no secret in this repo or the app. (Claude's knowledge, unverified: a browser app using the Microsoft login flow with PKCE needs an app ID but no client secret.)

### Decisions (2026-10-11)
- **Voice to text:** use the iPhone keyboard's dictation key in a text box. Audio recording (the voice memo, M1 step 6) stays optional.
- **Open question:** when is a recording deleted? Proposal: kept until the card is marked `processed`, then deleted unless the owner chooses to keep it.
- **Browser speech recognition is skipped.** WebKit bug 225298 (closed as deferred) says it was unavailable in Home Screen web apps.
- **Persistent storage (2026-10-11):** already requested on every launch by `src/status.js`; the footer shows the answer. MDN (local docs, "Storage quotas and eviction criteria"): persistent data is skipped when the device is short on space; Firefox asks the user, Safari and Chromium browsers decide silently from the user's history with the site. MDN describes Safari's 7-day deletion rule separately and does not say `persist()` exempts a site from it, so that stays unproven. The iPhone installed app answered "persistent". Not yet seen: the laptop browser's answer. Treat the request as a bonus, not protection: export is the backup (deleting the home-screen app deletes its data).
- **Photos are shrunk when taken (2026-10-12):** longer side at most 2048 px, JPEG quality 0.8, in `src/photo.js`. The shrunken copy is the only copy the app keeps. (Claude's belief, unverified: a photo taken through the app's camera button is not also saved to the iPhone Photos library.) Photos already stored are not changed. Rotation is applied by the browser when it decodes the image; tested in a Chromium-based browser only, so check portrait and landscape photos on the iPhone.
- **Offline update rule (2026-10-11):** the page (`index.html`) is network first, with a 4 s limit before falling back to the saved copy; scripts and styles are saved-copy first (their file names carry a fingerprint, so a saved copy is never an old version of the same name); each fresh page rebuilds the saved set and deletes unused files. The page fetch uses `cache: 'no-cache'` so the server is always asked whether the page changed (see Status). `public/sw.js` itself never changes, so phones never need to replace the worker.
- **Voice memos must be recorded with the app in the foreground** unless the lock-screen test is ever run (the owner skipped it on 2026-10-11, so it is untested, not failed).
